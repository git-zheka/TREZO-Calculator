# Модель даних і формули

Три колекції плюс один документ налаштувань. У режимі `db` це колекції сховища артефакту, у режимі `local` — три масиви в одному JSON під ключем `rider.v1`. Форма записів однакова.

---

## `orders` — замовлення

```jsonc
{
  "id": "k3f9a1b2c7d1",        // uid(), генерується на клієнті
  "date": "2026-07-12",        // ISO, дата події (не дата оплати)
  "clientId": "c4a1b2",        // → clients.id, порожній рядок якщо без замовника
  "clientName": "Клуб Atlas",  // денормалізована копія, щоб список не робив join
  "title": "Пʼятниця в Atlas", // «що робимо»
  "kind": "rent+set",          // rent | rent+set | set | other — довідково, у розрахунках не бере участі
  "currency": "UAH",           // UAH | USD — валюта всього замовлення
  "status": "done",            // lead | confirmed | done | cancelled
  "expenses": 400,             // дорога, паливо, помічник — у валюті замовлення
  "notes": "",
  "items": [
    { "type": "gear", "equipmentId": "g4", "name": "Світло Chauvet SlimPAR", "qty": 4, "price": 350 },
    { "type": "service", "name": "Діджей-сет 4 год", "qty": 1, "price": 6000 }
  ],
  "gcalId": "5hdud3ntp1afj0n4",   // id події в Google Календарі, null якщо не синхронізовано
  "gcalSig": "2026-07-12§Пʼят…"   // підпис стану на момент останнього запису в календар
}
```

**Чому `name` дублюється в позиції.** Позиція зберігає назву обладнання на момент замовлення. Якщо перейменувати картку через рік, старі замовлення читаються так, як їх виписували. Звʼязок для розрахунків тримає `equipmentId`, назва — для очей.

**Чому ціна лежить у позиції, а не береться з картки.** Дефолтна ставка з картки лише підставляється у форму. Збережене замовлення від картки більше не залежить: підняв прайс — минулі замовлення й окупність не переписалися заднім числом.

**Статуси.** У грошові розрахунки йде тільки `done`. `confirmed` і `lead` зайняті в календарі й у прогнозі завантаження, але не в доході й не в окупності. `cancelled` не входить нікуди, крім лічильника скасувань у підказці до графіка.

## `equipment` — картки обладнання

```jsonc
{
  "id": "g2",
  "name": "Колонки RCF ART 912-A",
  "category": "Звук",
  "qty": 2,                    // скільки одиниць у наявності — використовується детектором задвоєння
  "purchaseDate": "2026-05-04",
  "purchasePrice": 76000,
  "purchaseCurrency": "UAH",   // валюта покупки — база для окупності
  "rateUAH": 1800,             // дефолтні ставки оренди
  "rateUSD": 45,
  "status": "active",          // active | repair | sold — продане не показується у формі замовлення
  "notes": ""
}
```

---

## `clients` — замовники

```jsonc
{ "id": "c1", "name": "Промо-агенція Vector", "type": "agency" }
```

Створюються самі: якщо у формі вписати замовника, якого ще немає, `saveOrder()` заводить картку до збереження замовлення. Пошук по імені без урахування регістру.

## `settings/app`

```jsonc
{ "rate": 41.5, "gcalLast": "2026-09-03T11:33:00.000Z" }
```

`rate` — необовʼязковий курс долара для окупності, `0` = вимкнено.

# Формули

## Сума замовлення

```
total(order)   = Σ (item.qty × item.price)
net(order)     = total − expenses
gearPart(order)= Σ (item.qty × item.price)  де item.type === "gear"
```

Позиції типу `service` — своя робота, доставка, монтаж — у суму входять, в окупність обладнання **ні**. Інакше техніка «окуповувалась» би гонорарами, і цифра брехала б.

## Окупність одиниці

```
earnedSame  = Σ по всіх done-замовленнях у валюті покупки:  qty × price  для цієї одиниці
earnedOther = те саме, але в другій валюті
converted   = rate > 0 ? (cur === "UAH" ? earnedOther × rate : earnedOther / rate) : 0
earned      = earnedSame + converted

pct       = earned / purchasePrice × 100
perUse    = earned / uses                     // uses = скільки разів одиниця входила в done-замовлення
usesLeft  = ceil((purchasePrice − earned) / perUse)
```

**Чому саме так.** Коли на виїзді задіяно пʼять одиниць, класична задача — як розкласти гонорар між ними. Тут вона не виникає взагалі: замовлення складається з позицій, кожна позиція має свою ціну, тож кожна одиниця заробляє рівно свій рядок. Ніяких пропорцій і припущень.

**Валюти.** Гривня й долар не конвертуються ніде, крім цієї формули, і лише коли курс заданий вручну. Причина: техніка, куплена за долари, гривневими замовленнями інакше не окупається ніколи — окупність зависає на нулі при живому заробітку. Курс один на всю історію: це навмисне спрощення, точний облік вимагав би курсу на дату кожного замовлення.

## Розподіл по замовниках

```
частка замовлень = orders(client) / orders(усі)     // включно з lead і cancelled
дохід            = Σ total(order)  де status === "done", окремо по кожній валюті
концентрація     = частка топ-1 замовника; ≥ 50% → банер про ризик
затихлі          = last(client) старше 90 днів
```

Частка замовлень і частка доходу навмисно рахуються окремо. Це різні картинки: один дає багато дрібних виїздів, інший — два жирних на рік.

## Сезонність і спад

```
monthlySeries(12)  — 12 останніх місяців: count, UAH, USD, cancelled
дельта = (Σ останні 3 міс − Σ попередні 3 міс) / Σ попередні 3 міс × 100
byMonth[0..11]     — усі роки, згорнуті в 12 кошиків: де пік, де провал
```

Розкладка йде по `date`, тобто по даті події. Скасовані рахуються окремо і в `count` не входять.

## Задвоєна техніка

```
для кожної дати з ≥2 активними замовленнями:
  для кожної позиції gear: сума qty по всіх замовленнях цього дня
  якщо сума > equipment.qty → конфлікт
```

День обводиться червоним у календарі, під сіткою — список позицій, яких не вистачає. Скасовані замовлення не рахуються.
