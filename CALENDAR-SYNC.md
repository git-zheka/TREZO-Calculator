# Календар і синхронізація

Дві незалежні речі: календар усередині застосунку (працює завжди) і дзеркалення дат у Google Календар (працює лише у версії всередині Claude).

---

## Календар усередині

`renderCalendar()` малює сітку 7×6 з понеділка. Дні беруться з `state.orders`, згруповані по `date`.

- Колір лівої смужки = статус: жовтий `lead`, синій `confirmed`, зелений `done`, червоний закреслений `cancelled`.
- Клік по події відкриває замовлення, клік по порожньому місцю дня — створює замовлення з підставленою датою.
- Червона рамка дня = задвоєна техніка (формула в `DATA-MODEL.md`).
- Під сіткою — список замовлень місяця з сумами по валютах.
- На екранах до 640 px текст подій ховається, замість нього кольорові смужки-крапки, а роль списку бере на себе секція під календарем. Це не «спрощена мобільна версія» — на 50-піксельній клітинці текст усе одно нечитабельний, а список читається краще за сітку.

Тижні починаються з понеділка: `(date.getDay() + 6) % 7`.

## Запис у Google Календар

### Як це працює всередині Claude

Сторінка, опублікована як артефакт, може викликати конектори власника через капабіліті `mcp`. Оголошення при публікації:

```json
{
  "db": {},
  "mcp": { "servers": [{ "server": "Google Calendar",
                         "tools": ["create_event", "update_event", "delete_event"] }] }
}
```

Виклики йдуть під обліковкою того, хто дивиться сторінку; сторінка ніколи не бачить токенів. `server` — це відображувана назва конектора, не id.

```js
mcpCap = await window.claude.use("mcp");        // null → капабіліті недоступна
const list = await mcpCap.listTools();          // перетин маніфесту з реально підключеним
await mcpCap.callTool("Google Calendar", "create_event", args);
```

### Формат події

```js
{
  summary: "Пʼятниця в Atlas · Клуб Atlas",   // заявки отримують префікс "? "
  description: "Статус…\n\nСума…\n\nОбладнання:\n• …",
  startTime: "2026-07-12T00:00:00Z",
  endTime:   "2026-07-13T00:00:00Z",           // наступний день
  allDay: true,
  colorId: "9",                                // 5 заявка, 9 підтверджено, 10 виконано
  availability: "AVAILABILITY_BUSY",           // заявки — FREE, не блокують час
  notificationLevel: "NONE"
}
```

**Пастка з часовими поясами.** Для подій на весь день час треба передавати в UTC-опівночі (`…T00:00:00Z`). Якщо передати `…T00:00:00+02:00`, Google перерахує це в `22:00Z` попереднього дня — і подія стане на день раніше. Перевірено на живому API: з `+02:00` дата 4 січня перетворилась на 3 січня, з `Z` лягла правильно.

### Що синхронізується і коли

Після кожного збереження замовлення (`saveOrder`) і по кнопці «Синхронізувати» (`gcalSync`).

```
status === "cancelled" і є gcalId → delete_event, чистимо gcalId
gcalId є і gcalSig збігається     → пропускаємо, нічого не змінилось
gcalId є, підпис інший            → update_event
gcalId немає                      → create_event, зберігаємо id у замовлення
```

`gcalSig` — конкатенація дати, назви, замовника, статусу, валюти, суми і списку позицій. Дешевий спосіб не смикати API на кожен рендер. Лежить у самому замовленні, тож переживає перезавантаження.

Демо-дані не синхронізуються ніколи: `gcalSync()` виходить одразу при `state.demo`.

### Помилки

Кожен код помилки має свою дію, тому одного банера «щось пішло не так» тут немає — див. `gcalErrorText()`:

| Код | Що показуємо | Чи повторювати |
|---|---|---|
| `needs_reauth` | перепідключити конектор у налаштуваннях | ні |
| `server_not_connected` | додати конектор | ні |
| `selection_required` | обрати одне з кількох підключень | ні |
| `blocked_by_policy` / `approval_required` | політика акаунта не пропускає | ні |
| `server_unavailable` | сервіс не відповідає, спробувати за хвилину | один раз, і тільки для читання |
| `tool_error` | показати повідомлення від сервісу | ні |

Окрема обережність із записами: `server_unavailable` і `upstream_error` **не доводять**, що виклик не пройшов. Тому повторний запис — лише за новим натисканням користувача, ніколи автоматично. Цикл при першій же фатальній помилці переривається (`break`), щоб не втупитись у сотню однакових відмов.

## Якщо хостити самому

Капабіліті `mcp` існує лише всередині Claude. На своєму хості цей шлях відпадає, і варіантів залишається три.

**1. Файл `.ics` — те, що вже вбудоване.** Кнопка «Експорт .ics» на вкладці календаря в локальному режимі. `buildIcs()` збирає `VEVENT` на кожне активне замовлення з тими самими датами й описом. Імпортується в Google Календар, Apple Calendar, Outlook. Мінус: разовий знімок, не підписка — після змін файл треба вивантажувати заново.

**2. Підписка на `.ics`.** Якщо піднімеш будь-який HTTP-ендпоінт, який віддає той самий текст із `Content-Type: text/calendar`, Google Календар підписується на нього по URL і сам перечитує раз на кілька годин. Це найдешевший спосіб отримати живе оновлення без OAuth: віддавати `buildIcs()` статикою і перегенеровувати при змінах.

**3. Google Calendar API напряму.** OAuth 2.0, scope `https://www.googleapis.com/auth/calendar.events`, далі `events.insert` / `events.patch` / `events.delete`. Тіло події лягає майже один в один на те, що вище:

```json
{
  "summary": "…",
  "description": "…",
  "start": { "date": "2026-07-12" },
  "end":   { "date": "2026-07-13" },
  "colorId": "9",
  "transparency": "opaque"
}
```

Для all-day API приймає чисту дату без часу — тоді пастка з поясами зникає взагалі. Токен доведеться десь тримати, тобто зʼявляється бекенд, якого зараз немає.
