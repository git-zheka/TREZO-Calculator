# Модель даних

Чотири таблиці в Postgres. Схема — `db/schema.sql`, TypeScript-типи — `src/lib/types.ts`, формули — `src/lib/calc.ts`.

---

## `orders` — замовлення

```sql
id          text primary key
date        date not null          -- дата події, не дата оплати
client_id   text references clients(id) on delete set null
client_name text                   -- копія імені на момент замовлення
title       text                   -- «що робимо»
kind        text                   -- rent | rent+set | set | other, довідково
currency    text                   -- UAH | USD, на все замовлення
status      text                   -- lead | confirmed | done | cancelled
expenses    numeric                -- дорога, паливо, помічник
notes       text
items       jsonb                  -- позиції, див. нижче
```

Позиція в `items`:

```jsonc
{ "type": "gear", "equipmentId": "g4", "name": "Світло Chauvet SlimPAR", "qty": 4, "price": 350 }
{ "type": "service", "name": "Діджей-сет 4 год", "qty": 1, "price": 6000 }
```

**Чому jsonb, а не окрема таблиця.** Позиції незмінні після збереження і ніколи не потрібні окремо від замовлення — нормалізація дала б лише join на кожен рендер. Запит «де задіяна ця одиниця» покриває gin-індекс по `items`.

**Чому назва й ціна копіюються в позицію.** Перейменуєш картку через рік — старі замовлення читаються так, як їх виписували. Піднімеш прайс — минулі суми й окупність не перепишуться заднім числом. Звʼязок для розрахунків тримає `equipmentId`.

**Статуси.** У гроші йде тільки `done`. `confirmed` і `lead` зайняті в календарі й у прогнозі завантаження, але не в доході й не в окупності. `cancelled` не входить нікуди, крім лічильника скасувань у підказці до графіка.

## `gear` — картки обладнання

```sql
id, name, category
qty                integer   -- скільки одиниць у наявності, з цього детектор задвоєння
purchase_date      date
purchase_price     numeric
purchase_currency  text      -- база для окупності
rate_uah, rate_usd numeric   -- дефолтні ставки оренди, підставляються у форму
status             text      -- active | repair | sold, продане не показується у формі
notes
```

## `clients` — замовники

```sql
id, name, type, notes
```

Створюються самі: вписуєш нове імʼя у формі — `findOrCreateClient` заводить картку перед збереженням замовлення. Пошук по імені без урахування регістру.

## `settings` — один рядок

```sql
id = 1, rate numeric, ics_token text
```

`rate` — необовʼязковий курс долара для окупності, `0` = вимкнено. `ics_token` — секрет у URL календарної підписки, ротується кнопкою в застосунку.

## Дати

Скрізь рядки `YYYY-MM-DD`. З бази дістаються через `to_char`, а не як колонка `date`: драйвер робить із неї `Date` у зоні процесу, і `toISOString()` на машині за UTC зсуває день назад. Виступ 12-го стає виступом 11-го — класика.

Для подій «на весь день» у календарі межа — наступний день (`DTEND` = дата + 1).

# Формули

## Сума замовлення

```
total(order)   = Σ (item.qty × item.price)
net(order)     = total − expenses
gearPart(order)= Σ (item.qty × item.price)  де item.type === "gear"
```

Позиції типу `service` — своя робота, доставка, монтаж — у суму входять, в окупність обладнання **ні**. Інакше техніка «окуповувалась» би гонорарами, і цифра брехала б.

## Окупність одиниці

```
earnedSame  = Σ по всіх done-замовленнях у валюті покупки:  qty × price  для цієї одиниці
earnedOther = те саме, але в другій валюті
converted   = rate > 0 ? (cur === "UAH" ? earnedOther × rate : earnedOther / rate) : 0
earned      = earnedSame + converted

pct       = earned / purchasePrice × 100
perUse    = earned / uses                     // uses = скільки разів одиниця входила в done-замовлення
usesLeft  = ceil((purchasePrice − earned) / perUse)
```

**Чому саме так.** Коли на виїзді задіяно пʼять одиниць, класична задача — як розкласти гонорар між ними. Тут вона не виникає взагалі: замовлення складається з позицій, кожна позиція має свою ціну, тож кожна одиниця заробляє рівно свій рядок. Ніяких пропорцій і припущень.

**Валюти.** Гривня й долар не конвертуються ніде, крім цієї формули, і лише коли курс заданий вручну. Причина: техніка, куплена за долари, гривневими замовленнями інакше не окупається ніколи — окупність зависає на нулі при живому заробітку. Курс один на всю історію: це навмисне спрощення, точний облік вимагав би курсу на дату кожного замовлення.

## Розподіл по замовниках

```
частка замовлень = orders(client) / orders(усі)     // включно з lead і cancelled
дохід            = Σ total(order)  де status === "done", окремо по кожній валюті
концентрація     = частка топ-1 замовника; ≥ 50% → банер про ризик
затихлі          = last(client) старше 90 днів
```

Частка замовлень і частка доходу навмисно рахуються окремо. Це різні картинки: один дає багато дрібних виїздів, інший — два жирних на рік.

## Сезонність і спад

```
monthlySeries(12)  — 12 останніх місяців: count, UAH, USD, cancelled
дельта = (Σ останні 3 міс − Σ попередні 3 міс) / Σ попередні 3 міс × 100
byMonth[0..11]     — усі роки, згорнуті в 12 кошиків: де пік, де провал
```

Розкладка йде по `date`, тобто по даті події. Скасовані рахуються окремо і в `count` не входять.

## Задвоєна техніка

```
для кожної дати з ≥2 активними замовленнями:
  для кожної позиції gear: сума qty по всіх замовленнях цього дня
  якщо сума > equipment.qty → конфлікт
```

День обводиться червоним у календарі, під сіткою — список позицій, яких не вистачає. Скасовані замовлення не рахуються.
