# Райдер

Облік прокату звуку та світла: замовлення, замовники, парк обладнання, окупність кожної одиниці, календар зайнятості.

Один HTML-файл без збірки, без залежностей, без бекенду. Уся логіка — ванільний JS усередині файлу. Шрифти тягнуться з Google Fonts, усе інше локальне.

---

## Що в пакеті

| Файл | Що це |
|---|---|
| `rider-local.html` | Готова до запуску версія. Відкрити подвійним кліком у браузері — працює. |
| `rider.artifact.html` | Той самий код без `<!doctype>`, `<html>`, `<head>`, `<body>` — форма, у якій сторінка публікується як артефакт Claude. |
| `DATA-MODEL.md` | Структури даних і формули всіх метрик. |
| `CALENDAR-SYNC.md` | Як влаштований запис у Google Календар і що робити при самостійному хостингу. |

Різниця між двома HTML — тільки в обгортці документа. Логіка байт-у-байт та сама, тому правку варто робити в одному файлі й переносити в другий.

## Запуск

```bash
# просто відкрити
xdg-open rider-local.html        # linux
open rider-local.html            # macos
start rider-local.html           # windows

# або підняти локальний сервер, якщо хочеться нормального origin
python3 -m http.server 8000
# → http://localhost:8000/rider-local.html
```

Дані лягають у `localStorage` під ключем `rider.v1`. Це означає: один браузер, один пристрій, ніякої синхронізації. Файл із `file://` теж працює, але кожен браузер матиме свою копію даних.

## Три режими сховища

Код визначає режим на старті, у `boot()`:

```
mode = "db"      → сторінка відкрита як артефакт усередині Claude.
                   Дані в серверному сховищі артефакту, живуть між пристроями,
                   доступний прямий запис у Google Календар.

mode = "local"   → усе інше, де працює localStorage.
                   Дані в браузері, замість запису в календар — експорт .ics.

mode = "memory"  → localStorage заборонений (приватне вікно з жорсткими налаштуваннями).
                   Сторінка рендериться, але нічого не зберігає.
```

Уся різниця сконцентрована у трьох функціях: `put()`, `del()`, `saveSettings()`. Щоб підключити свій бекенд, додай четверту гілку в кожну з них — решта коду про сховище не знає.

```js
async function put(coll, obj){
  // ...оновлення state...
  if(mode==="local"){ Local.write(); return; }
  if(mode==="api"){ await fetch(`/api/${coll}/${obj.id}`, {method:"PUT", body:JSON.stringify(obj)}); return; }
  if(mode!=="db" || !db) return;
  const {id, ...body} = obj;
  await db.collection(coll).doc(id).set(body);
}
```

## Демо-дані

Якщо сховище порожнє, сторінка показує вигаданий приклад із банером «Це приклад». Перший реальний запис його стирає назавжди — див. початок `put()`. Демо ніколи не пишеться у сховище і ніколи не потрапляє в Google Календар (`gcalSync()` виходить одразу, якщо `state.demo`).

Сам набір — у `demoData()`. Дати згенеровані відносно поточного місяця, тому приклад завжди виглядає свіжим.

## Структура коду

Файл читається зверху вниз, розділи позначені коментарями-банерами:

```
<style>                     токени теми, компоненти, мобільні правила
<header> <main>             статична розмітка: шапка, вкладки, 4 порожні секції
<script>
  helpers                   форматування грошей, дат, українські множини
  state                     єдиний обʼєкт стану + режим сховища
  demo data                 приклад
  derived                   orderTotal, gearEarnings, payback, clientStats, monthlySeries
  charts                    barChart + tooltip, без бібліотек
  views                     renderOrders / renderCalendar / renderGear / renderClients / renderStats
  calendar                  сітка місяця, детектор задвоєної техніки
  google calendar           mcp-капабіліті, побудова події, синхронізація
  ics                       офлайн-заміна синхронізації
  order form                драфт + модалка
  gear form                 драфт + модалка
  storage                   put / del / subscribe / boot
  wiring                    делеговані слухачі на document
```

Рендер тупий і повний: будь-яка зміна викликає `render()`, який перемальовує активну вкладку цілком через `innerHTML`. При сотнях замовлень це не проблема; якщо колись стане — вузьке місце буде в `renderOrders`, і лікується воно рендером списку по діапазону дат.

Слухачі подій — делеговані на `document`, тому перемальовування не потребує перепідписки. Атрибути, які щось роблять:

| Атрибут | Дія |
|---|---|
| `data-view` | перемикання вкладки |
| `data-open` | відкрити замовлення |
| `data-opengear` | відкрити картку обладнання |
| `data-newday` | створити замовлення на цю дату |
| `data-cal` | `-1` / `1` / `0` — попередній місяць, наступний, сьогодні |
| `data-act` | `new`, `newgear`, `saveorder`, `delorder`, `savegear`, `delgear`, `gcalsync`, `ics` |
| `data-o` | поле драфта у формі |
| `data-add` / `data-svc` / `data-del` | позиції замовлення |

## Тема

Три стани, не два: явний вибір ставить `data-theme` на корені, а типове «як у системі» не ставить нічого. Тому всі кольори оголошені токенами в голому `:root`, а темні значення дублюються двічі — у `@media (prefers-color-scheme: dark)` з ґардом `:root:not([data-theme="light"])` і в `:root[data-theme="dark"]`. Жоден колір не має єдиного визначення всередині медіа-блоку — інакше в нестемпленому стані сторінка ловить текст однієї теми на фоні іншої.

Шрифти: Unbounded (заголовки), Commissioner (текст), IBM Plex Mono (цифри й підписи). Усі три з кирилицею. Якщо тягнути з Google Fonts не хочеться — заміни `<link>` на локальні `@font-face`, фолбек-стек уже прописаний.

## Що варто додати наступним

- **Відмови й скасування як окрема сутність.** Зараз статус `cancelled` є, але заявки, які не дійшли до замовлення, ніде не фіксуються. Саме вони показують спад раніше, ніж дохід.
- **Вибір календаря.** Події летять у основний Google Календар. Окремий календар «Райдер» вимагає поля `calendarId` у `gcalArgs()` і селекта в налаштуваннях.
- **Резервна копія.** Кнопка експорту/імпорту всього стану в JSON — п'ять рядків поверх наявного `Local.write()`, а страхує від очищення браузера.
- **Знос обладнання.** Поле «ресурс» і попередження після N виїздів; для дим-машин і ламп це реальніше за окупність.
